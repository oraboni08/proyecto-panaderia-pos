Asíncrono · por lotes, no frena la caja

API Gateway

Nginx enruta /api/v1/* a cada servicio; el cliente nunca ve los puertos internos.

Database per service

Cada servicio es dueño de su base; el exportador pide los datos por API, no a la base.

CQRS

Escribir (sales_db) y leer reportes (reports_db) son modelos y servicios separados.

Asincronía / eventos

Cada venta es un evento que viaja al data lake sin bloquear la caja.

Jhon Jairo · 50 s. Línea continua = síncrono: el navegador solo habla con el API Gateway (Nginx), que enruta a cada servicio; sales llama a catalog para validar productos y precios. Cada servicio tiene su base dentro de un PostgreSQL. Línea punteada = asíncrono: cada 60 s el exportador pide a sales las ventas nuevas (por API, con token de servicio) y las escribe en HDFS; Spark procesa el histórico en paralelo y deja los resultados en reports_db, que solo lee reporting-service. Eso es CQRS: el modelo que escribe (Command, sales) es distinto del que se lee (Query, reporting). Si preguntan por EDA: el flujo es asíncrono y orientado a eventos de venta, pero sin broker; el exportador consulta por lotes. Poner RabbitMQ/Kafka es la mejora natural.

Seguridad y límites

Contraseñas y llave JWT como Docker secrets (/run/secrets), usuario sin root y un límite de memoria por servicio.

RUN pip install -r requirements.txt COPY app ./app # capa aparte: rebuild rápido USER panaderia # no corre como root HEALTHCHECK --interval=15s \ CMD urlopen(".../sales/health") CMD uvicorn app.main:app --port 8003
Victoria · 30 s. Cada servicio tiene su Dockerfile: imagen base slim, primero dependencias (Docker reutiliza esa capa si solo cambia el código), usuario sin privilegios y un HEALTHCHECK: si la réplica deja de responder, Swarm la reemplaza. Las claves no están en el código: son Docker secrets montados en /run/secrets. Cada servicio tiene límite de memoria porque el PC tiene 7,4 GB (reto 1).

Orquestación · Docker Swarm

Un stack, dos redes, cero IPs fijas.

Stack declarativo

docker stack deploy -c docker-stack.yml panaderia
Un archivo describe los 13 servicios, réplicas, redes, secrets y configs. Swarm mantiene ese estado.

2 redes overlay

pos_net tráfico de la app · monitoring_net solo para que Prometheus lea /metrics. Grafana no ve la base de datos.

DNS + VIP

Los servicios se llaman por nombre (sales-service). Swarm da una IP virtual y reparte entre réplicas (IPVS). tasks.<svc> devuelve cada réplica.

Routing mesh · solo 4 puertos publicados

:80Gateway (interfaz + API):3000Grafana
:9090Prometheus:9870HDFS NameNode

Actualizar sin apagar

update_config: una réplica a la vez, start-first (la nueva arranca antes de bajar la vieja) y rollback automático si falla. Configs inmutables versionados (_v2).

Victoria · 40 s. Todo se despliega con un comando y un archivo. Swarm compara el estado deseado con el real y lo corrige. Dos redes overlay aisladas: la app y el monitoreo. Nadie usa IPs: el DNS interno de Swarm resuelve el nombre del servicio a una IP virtual (VIP) que balancea entre réplicas; Prometheus usa tasks.servicio para ver cada réplica por separado. Hacia afuera solo 4 puertos por el routing mesh. Las actualizaciones son rolling: start-first y rollback automático. Si preguntan por nodos: es un Swarm de 1 nodo (manager) por la RAM; con docker swarm join se suman workers sin cambiar el stack.

Alta disponibilidad y recuperación ante fallos

Si una réplica muere, la caja ni se entera.

1

2 réplicas de cada servicio con estado

auth, catalog, sales, reporting, gateway y frontend. La VIP solo envía tráfico a las réplicas vivas.

2

El gateway reintenta

proxy_next_upstream: si una réplica falla a mitad de la petición, Nginx la repite en la otra.

3

Swarm repone lo que falta

restart_policy: any + HEALTHCHECK: si una réplica cae o deja de responder, crea otra.

11 s

También: el exportador se mató y Swarm lo recreó en 11 s, retomando desde el último id guardado en HDFS, sin duplicar ventas.

Victoria · 30 s. Tres capas: réplicas (la VIP solo manda tráfico a las vivas), el gateway reintenta en otra réplica y Swarm repone la que falta (restart_policy + healthcheck). Prueba: con peticiones continuas borramos a la fuerza una réplica de sales: 60 de 60 respondieron y en 11 s había 2/2 otra vez. «Lo van a ver en el video, capítulo 3: matamos la réplica y la caja sigue vendiendo con Nequi.» Punto único de falla honesto: PostgreSQL y el NameNode tienen 1 réplica (Swarm los reinicia, pero no hay réplica caliente); la mejora sería replicación de Postgres y HDFS HA.

Retos enfrentados · 24 documentados

Lo que no salió a la primera.

02
SQLite no sirve con réplicas

Cada réplica tendría su propio archivo. → PostgreSQL compartido, una base por servicio.

04
Dos réplicas cargando datos a la vez

Condición de carrera al arrancar. → Candado de PostgreSQL (pg_advisory_lock).

11
El gateway se caía al arrancar

Nginx resolvía nombres una sola vez. → DNS de Swarm por petición + reintento en otra réplica.

19
Spark no leía los bloques de HDFS

El NameNode registró la IP del NAT de la overlay. → Conectar al DataNode por nombre de host.

17
Configs de Swarm inmutables

No se pueden editar en caliente. → Versionar el nombre (_v2) y rolling update.

24
Grafana decía «0 ventas»

El contador nacía en 1 y increase() no veía el salto. → Inicializar las etiquetas en 0.

Otros: RAM de 7,4 GB (límites por servicio), servicios antes que PostgreSQL (reintentos), hora UTC (tzdata), imágenes latest sin actualizar (--force), archivos pequeños en HDFS (por mes), bug del domingo heredado del Proyecto 1.
